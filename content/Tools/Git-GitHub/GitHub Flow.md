准确的说，Github Flow 的标准工作流程，分为两种工作模式。一种是多人协同工作模式。一种是开源项目工作模式。

# 一、多人协同工作模式

首先项目负责人将项目仓库创建好，推送到远程共享仓库中。作为团队开发者，工作流程如下
### Step 1：首次将项目克隆到本地

```shell
git clone <远程仓库地址>
```

克隆的方式等效于多个 git 操作，即 `git clone` = `git init` + `git add remote` + `git fetch` + `git checkout main` 。但是大多数情况下，我们直接使用 clone 就可以了。 

>- 首次加入项目的时候，会执行这一步。后面就不用做 clone 了。
### Step 2: git pull 更新分支

切换到本地 main 分支，用 git pull 拉取 main 分支最新的状态，确保目前本地的 main 是和远程仓库同步的最新状态。`git pull = git fetch + git merge`

```shell
git checkout main
git pull                    # 确保 main 是最新的
```

>- 这一步在第一次 clone 项目时可以省略，因为刚 clone 下来的状态肯定是最新。但是后续开发过程中，是不是要执行 `git pull`，更新本地的 main 分支到远程仓库的最新状态.
### Step 3: 在 main 上创建自己的分支

```shell
git checkout -b myfeature # 从最新的 main 开新分支 myfeature 并切换到myfeature上去。
```

> 创建分支，就是在当前分支的状态基础上，以它为初始状态，新建一个分支。
> 新建分支都是以现有分支为基础 (准确的说，是以现有分支的某个提交点为基础) 或者为初始状态进行创建的。首个分支，是执行 git init 时，Git 初始化为仓库，创建了main分支的名字或指针，第一次执行 git commit 时，创建第一个分支 main，它就包含了项目目录的当前文件和快照信息作为第一个提交点。此后在这个仓库中的所有新建分支，都必须基于某个提交点或者说分支。
> 创建分支，详见 [Git merge 原理详解](./Git%20merge原理详解)

### Step 4: 在自己的分支上开发，多次提交

```shell
# 多次 commit
git push origin myfeature  # 第一次推送，分支出现在远程
```

我们通常在自己本地的新建分支 myfeature 上进行开发，开发过程中，会有多次 commit, 并推送至远程仓库中对应的 myfeature 分支进行更新。

注意⚠️，我们推送的自己的开发分支，远程仓库中更新的也是我们个人自己的开发分支。不要推送到主分支 main 上。

### Step 5 : 开发完成后，再次同步一下远程的 main 分支

在我们开发期间，main 分支有可能会发生变化，所以我们要更新 main 分支。更新的时候，先拉远程的 main 到本地，让本地的 main 先完成 merge。再切换到 my-feature 分支，让它 merge 本地的 main。这是为了避免冲突. 然后再推送到远程。
如果是第一次提交，远程仓库中就会新建一个 my-feature 分支。

```bash
git checkout main
git pull
git checkout my-feature
git merge main              # 或 git rebase main
git push origin my-feature
```

> 执行 git check out main 和 git pull 之后，本地的 main 分支就是最新状态。git checkout my-featrue 如果就是在刚刚更新的main分支上创建的，那后面的 merge main 就是多余的。
> 但是，除开第一次 git checkout my-feature 是在 main 分支上创建新分支，后续该操作只是切换到 my-feature 分支作为当前分支。这种情况就是继续开发的旧分支。它首先要将 main 分支合并到 my-feature 分支，让 my-feature 分支获得主分支最新的提交，这样推送到远程 my-feature 分支上，提起 PR 的时候，就可以避免冲突。这是这个工作流程的原理。详细关于 git merge的原理，参考 [Git merge 原理详解](./Git%20merge原理详解)

### Step 6: 发起 PR 

在 GitHub 网页上点击发起 PR，等 review。Review 过程中，如果 reviewer 提了修改意见，你在本地改完 commit，再 push 到同一个分支，PR 会自动更新。

### Step 7: Merge完成，删除分支

**Merge 之后**， 即维护者合并 PR 后，你这个分支的使命就完成了。本地和远程的 my-feature 分支都可以删掉：

```bash
git checkout main
git pull                    # 把合并结果拉下来
git branch -d my-feature    # 删本地分支
git push origin --delete my-feature  # 删远程分支
```

然后开始下一个功能时，重新从 main 拉新分支。

### 总结

> [!NOTE] 标准GitHub Flow
>首先 git clone 项目到本地(首次)。git pull 拉分支保持更新(首次之后开始)。开一个自己的分支，在自己的分支上往后开发。开发完成后，为了避免在此期间远程仓库中的main发生了变化，再git pull 一次更新本地 main，再在自己的分支上 merge 本地 main，让自己的分支也处于最新状态. 推送自己的分支到远程仓库，确保没问题后，发起一个PR。等待维护者审核，审核通过后，远程仓库的主分支 merge 我们提交的分支。然后，本地和远程的我们的开发分支都可以删除了。下一个功能，重新从 main 开一个新分支来开发。

我们多个人都拉同一个仓库里面的分支, 然后直接在这个分支上开发，推送也直接推送给远程仓库中的这个分支，本质上就是多个人在同一个分支上往后开发，不断提交更新该分支的状态。
把仓库分支拉下来，创建自己的分支，在自己分支上开发，然后推送到远程，并请求PR的方式，就是每个人有一个自己的开发分支。这是两种不同的方式。

> [!NOTE] 最佳实践
> 一般1～3人的小项目，或者是自己的项目，就采用直接在main上开发，pull/push，这样效率最高。但是更大的团队或者开源项目，就采用feature分支 + PR 的方式，更加安全可控

# 二、开源项目工作模式

开源项目的贡献者，可以是任何人，所以项目官方为了保证官方仓库不被污染和恶意提交攻击，基本上不允许除了项目维护人员之外的人，直接向官方仓库推送分支。而是项目方接受 PR 申请，直将 PR 审核通过的分支 merge 到主分支上，而这中间项目维护方，并不接受本地的直接申请 PR，而直接收 fork 仓库的 PR 申请。

开源项目的工作模式，与多人协同工作模式相比，多了一个 fork 仓库做中转，其他的工作流程和原理，大体一致。
## 开源项目 PR 提交流程 
### `◼︎` Stage 1: fork 项目，开发功能，提交 PR 

开源贡献者，首先将开源项目整个仓库 fork 到远程仓库托管平台的个人账号下，也就是在仓库托管平台上的个人账号下，创建一个新的仓库，这个仓库就是开源项目仓库的副本，这个操作就是 fork。然后把项目拉到本地，在本地仓库中新开一个分支开发新功能，期间根据开发进度，不断推送到远程的 fork 副本仓库上(不是项目官方仓库)，开发完成后是通过这个 fork 副本仓库，去向官方申请 PR。等待维护者审核。

审核通过后，项目方维护者直接在 Github 上点击 Merge, 合并分支. 我们开发分支就可以删除了。下次开发新功能，就单独再开一个新分支。
### `◼︎`Stage 2: PR 完成后更新 main 分支

PR 完成后，我们要更新本地仓库和 fork 仓库的 main 分支，让它们与官方仓库的 main 分支保持同步(最新的 main 分支已经包含了我们开发的功能)。

首先，本地切回 main 分支, 然后获取远程官方仓库的最新状态，让本地 main 分支更新到官方 main。然后再把本地的 main 分支推送到 fork 仓库更新 fork 副本的 main 分支。这样，本地仓库的main 分支和 fork 副本仓库的 main 分支，都和官方仓库的 main 分支完成了同步。

```bash
# 1. 回到本地主分支
git switch main

# 2. 获取官方仓库的最新状态
git fetch upstream

# 3. 让本地 main 更新到官方 main
git merge --ff-only upstream/main

# 4. 把最新 main 推送到你的 Fork
git push origin main
```

### `◼︎`Stage 3 : 删除旧分支

PR 完成，我们的开发内容，就已经在最新的 main 分支上了。然后更新了本地和 fork 仓库的 main 分支，旧的开发分支就可以删除了。删除的时候，我们在本地先删除本地开发分支，再删除远程 fork 仓库中的开发分支(因为 fork 仓库在我们自己的账号下，我们有这个权限)。

```bash
# 删除本地开发分支
git branch -d feature-a

# 删除 Fork 仓库中的远程开发分支
git push origin --delete feature-a
```

### Stage 4: 新开分支，开发新功能

```
提交 PR --> 审核合并 --> 更新 main 分支 --> 删除旧分支 --> 新开分支，开发新功能
```

PR 整个流程执行完成后，我们要开发下一个功能的时候，我们再在本地重新新开一个分支，假设叫 feature-b，然后推送到远程 fork 仓库中，然后再用 fork 仓库的 feature-b, 向官方提交 PR。

# 3. 对比

多人协同工作模式，和开源项目工作模式，本质上是一样的。只不过，开源项目工作模式，为了安全，在中间多设置了一层中转。

开发者将自己的开发分支提交到自己账号全权拥有的项目 fork 副本仓库中，而不是直接提交到官方仓库。开发者在自己的副本仓库中整理好了分支，再从副本仓库中提交 PR。项目维护者，审核副本仓库中的分支，如果符合审核，就 merge 到官方主分支上。

开源项目工作模式的整个过程，任何用户都不能直接触碰项目官方仓库，只能在自己的副本中操作，官方仓库的变动，都是维护者审核了用户提交到副本上的分支后，自己手动合并的，非官方人员，全程与官方仓库保持隔离。这最大程度的保证了安全。

而普通的多人协同工作模式，所有 team members 都是直接往项目上推送自己的分支，开发完成后，提 PR，由项目经理或同事审核，然后合并。中间没有中转这一层。
