# 1. 分段分析

如果遇到 TTFT 偏高，但是推理服务自身的 TTFT 保持稳定的情况下，就是在网关侧进行排查。注意网关侧分为几段。

| 时间点 | 含义                   |
| --- | -------------------- |
| t0  | 网关收到请求               |
| t1  | 网关向推理服务后端发出请求        |
| t2  | 网关收到上游首个有效 token     |
| t3  | 网关向客户端 flush 该 token |

严格说，最前面还有一段「客户端向网关发出请求」，不过这一段如果出问题，那就是网络问题，与我们本身的系统无关。

在排查问题时，我们重点观察 `t1-t0` 和 `t3-t2`: 
`t1-t0` 主要是网关排队，鉴权，路由的等待时间。
`t3-t2` 主要是流式响应的缓冲或转发延迟。
另外，`t2 - t1` 反应的就是推理服务的延迟，并且它包含网络延迟。

> [!NOTE] 分段分析
> 排查故障的时候。总体上在两端进行分析。「模型推理后端」和「流式网关」。这里假设模型后端没有问题，重点关注「流式网关」。
> 排查网关问题时，要分段分析：

> 主要是关注请求在「网关排队处理时间」以及模型响应后「网关转发响应」给客户端的时间。

# 2. 对同一个请求关联 request_id

「对同一个请求关联 request_id」意思是，<font color="orange">用同一个请求的唯一编号 (request_id) 把同一个请求在不同处理阶段产生的记录串起来，分析这个请求在系统中的行为</font>。

系统会同时并发的处理很多请求，日志会交错出现。因此，一个请求进入系统时，通常会生成一个 `request_id`, 后续处理和调用下游服务时会携带这个编号，写日志也记录它。

> [!example] request_id 筛选日志
> 例如，我们可以在日志中筛选 `request_id=req_123`, 得到网关上的以下日志。时间是从网关收到该请求开始计算的。
> ```
> request_id=req_123 网关收到请求          +0 ms
> request_id=req_123 网关向后端发出请求     +800 ms
> request_id=req_123 网关收到首个 token    +1000 ms
> request_id=req_123 网关转发首个响应token  +1005 ms
> ```
> 通过这样的日志就可以还原这次请求
> - 请求发往后端之前，在网关停留了 800 ms
> - 发往后端后，到收到首个响应 token, 花了 200ms, 包含网络和后端的推理时间
> - 收到首个响应 token 后，到把这个 token 转发回客户端，网关用了 5 ms。
> 
> <font color="orange">这就是「关联同一个 request_id」：按编号找到属于同一次请求的记录，再分析各阶段耗时。</font>

注意⚠️：上面的例子我们只分析了 Nginx 网关的日志。完整的请求日志，是各层分别记录的。
在 `客户端 -> nginx网关 -> 推理网关 -> 推理服务`  这样的架构中。一个请求会让 <font color="#45c36e">「nginx入口网关」</font>，<font color="#45ce6e">「后端推理服务的 API 层」</font>，和 <font color="#45ce6e">「推理引擎内部」</font>，三个部分产生这个请求的日志，所以<font color="orange">「关联同一个请求的 request_id」</font>, 就是要把这三个部分的日志中，同一个请求的部分串起来，分析该请求在各个部分的行为，串起来就是通过 request_id。

> [!info] 三个部分内容
> - Nginx 网关:  接受外部请求，反向代理，可承担 HTTPS 和负载均衡，连接上游，转发请求。
> - 后端推理服务 API 层：收到请求，解析和校验，提交推理任务，收到首个 token，封装成 JSON 或 SSE 向外发送。这就是常说的「推理网关」，它不一定是单独部署的网关，也可能是推理服务自带的 HTTP API 层。比如使用 vLLM 的话，这一层就是 vLLM 自带的。
> - 推理引擎内部：调度请求，执行 prefill, 逐步生成 token。

例如，同一个 request_id 编号可以串起：

```
request_id=abc_123
  -> Nginx 接受请求
  -> 后端 API 收到请求
  -> 推理引擎排队，执行，生成首个 token
  -> 后端 API 发送首个 token 给 Nginx
  -> Nginx 转发回客户端。
```

# 3. 延迟排查

总结：如果出现了 TTFT 偏高或者延迟偏高，排查原因的过程主要集中在两个侧，「网关侧」和「推理侧」。
## 推理侧

如果 GPU 的利用率快接近 100%，就说明 GPU 的负载快要满了，GPU 的负载主要用于做。prefill 计算。此时可以降低并发度，降低上下文长度，可以减轻 GPU 的负载，减少请求数量竞争 GPU 或者减少单个请求对 GPU 的需求(降低上下文). 这样可以降低单个请求的 TTFT 和延迟。
另外也可以扩展机器，增加算力，保证并发的提高系统的处理能力。

如果 KV Cache 的资源紧张，导致请求排队的数量增加，或者出现出现大量抢占，那么就会出现TTFT 增大，延迟增加。在显存有余量的情况下，可以提高显存使用率，用更多的 KV Cache 提高并发，减少抢占降低延迟。如果是 KV Cache 的命中率低，就需要进一步观察，有可能刚好来了一批新的请求，集中导致 prefill 计算，延迟升高，正常情况下观察一段时间，延迟可能恢复正常。

如果 GPU 利用率正常，KV Cache 的命中率和占用率也都正常，这时就需要考虑通信问题。如果使用 TP，All-Reduce 规约求和的时候，是否 GPU 间的通信出现了瓶颈。通信带宽出现瓶颈，那可能需要考虑硬件升级优化的问题。

此外，如果使用的是 PP，是否出现了流水线空泡的问题，如果有流水线空泡问题，就需要考虑使用 microbatch，将流水线填满。

## 网关侧

在网关侧，需要分段分析。
- 如果请求到达量与实际放行量差别很大，检查排队，鉴权，限流和错误，重点检查 429 和 503。

> [!tip] Nginx 上的 429 和 503 错误
> - 429 Too many requests: 请求频率超过了配置频率限制。比如某个 IP 或 API 请求超额。注意⚠️，<font color="orange">这是客户端错误</font>，这个客户端受限，但是其他客户端正常。
> - 503 Service Unavailable: 服务器无法处理请求，常常是过载和限流。这里的过载限流，是<font color="orange">服务器端错误</font>，是整个服务器端限流，针对的是所有客户端进行限流。

- 如果请求转发上游模型后端到收到第一个 token 的时间过长，则检查网关到后端服务的网络情况和推理侧问题。
- 如果收到响应到发送 SSE 回客户端的时间过长，检查 buffering 是否关闭，SSE 封装是否正常。

总之，如果确定 TTFT 升高是网关侧的问题，那就在网关侧分段排插。<font color="orange">依次查看，请求排队，鉴权，限流，错误率，连接上游后端，buffering 设置，SSE 封装等</font>。
