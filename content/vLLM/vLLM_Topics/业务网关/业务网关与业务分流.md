通常我们部署大模型的时候，架构为

![700](mermaid-diagram.png)

- <font color="orange">「Nginx」</font> 是支持流式转发的 HTTP 反向代理入口。它可以承担 HTTPS，负载均衡和连接管理。这层可以按部署的需要选择，并非 vLLM 必须依赖的组件。
- <font color="orange">「业务网关」</font>主要是在请求送入模型部署之前，进行业务识别，检查豁免资格，应用不同的上下文限制，控制并发与配额，排队等。总之，在网关层面先对业务请求进行一轮筛选过，所以它叫做业务网关。
- <font color="orange">「API Server」</font> 是 vLLM 自带的 API Server，它主要接受 HTTP 请求，提供兼容 OpenAI 的接口，校验请求参数，返回流式结果等。API Server 和后面的 “大模型部署” 通常同属一套 vLLM 部署。API Server 处理 HTTP 和输入输出，推理引擎负责调度，KV Cache 管理，GPU Worker 执行模型计算。

# 1. 业务网关

后端部署大模型，vLLM 通常只能按统一规则部署一套大模型服务实例。但是，我们的业务可能有多种类型，而不同业务类型可能需要不同约束条件。

比如对于某种核心业务，可能允许它拥有超长的上下文长度，但超长上下文会导致 KV Cache 能并发的请求数减少，所以针对这种业务可能需要一套专门的约束条件，独立的上下文长度，独立的并发控制，独立的排队规则等。

后端 vLLM 部署的大模型服务，只会按照部署参数对请求进行筛选，调度，过滤。但是，它无法在业务层面对请求进行区分，标准 vLLM 不会收到一个 「特殊业务」标签，就自动切换整套业务规则，在业务层面的控制就是在业务网关侧实现的。

业务网关负责上下文权限，配额以及发往后端大模型服务的在途并发控制。vLLM 后端大模型服务则按统一的引擎配置调度。进入 vLLM 实例后，多类请求仍然共享 GPU 和 KV Cache，不同类型业务的长短请求之间仍会相互影响。再次强调，<font color="orange">在 vLLM 实例侧，不在业务层面对请求进行区分</font>。


> [!tip] 多套放行和调度规则
> 我们可以根据业务，划分出多套放行和调度规则。不同的业务请求，可以有自己独立的一套限制规则，这样更加符合业务特点。
> 相当于把控制前移了，我们自己针对业务写每个业务独立的限制规则，不完全依赖后端 vLLM 统一的部署参数。这样就在业务层面对不同的业务进行了定制化限制。

# 2. 两层网关限制

在具有业务网关的模型架构中，就具有<font color="orange">「两层网关限制」</font>，一层是<font color="orange">「业务网关层」</font>，一层是<font color="orange">「模型部署层(vLLM)」</font>。请求必须同时满足两层约束。
- 业务网关层：按业务类别设置上下文上限，并发上限，在途 token 预算和豁免规则，决定请求何时放行。
- 模型部署层(vLLM): 通过模型启动和部署参数，`max_model_len`, `max_num_seqs`, `max_num_batched_tokens` 等参数，约束实际的推理执行。
网关放行，只代表请求允许进入后端，不代表立即执行，也不能突破后端上限。业务层面的多套放行规则，是网关侧根据业务特点进行的业务限制。

所以，在架构中，分为两层网关

|层次|负责什么|
|---|---|
|**业务网关**|识别业务、检查豁免资格、应用不同上下文限制、控制并发与配额、排队|
|**vLLM 自带 API Server**|接收 HTTP 请求、提供兼容 OpenAI 的接口、校验请求参数、返回流式结果等|
|**vLLM 推理引擎**|模型执行、批处理调度、KV cache 管理|


```
调用方
  ↓
业务网关：普通 / 豁免两套规则
  ↓
vLLM 自带 API Server
  ↓
同一个模型推理引擎
```

这套业务规则可以放在外部网关，也可以通过自定义中间件接入 vLLM 的 HTTP 服务；后一种需要自行开发，不能仅靠默认配置就自动获得上述能力。

# 3. 请求池分流

例如，默认的上下文长度导致关键业务效果受影响时。就应该放开关键业务限制，设置豁免机制。按业务场景或任务类型生效。

我们可以把普通短请求和获准使用长上下文的请求分流，设置<font color="orange">「专用业务的长请求池」</font>，专用请求池涉及两层策略。
- 豁免策略：业务网关处要识别和决定，哪些业务可以突破默认上下文限制。
- 请求池与调度：专用请求池中的长请求，如何排队，使用多少资源等。
注意⚠️：识别业务并执行不同规则的主体是业务网关，请求在网关处进行分流，执行不同的限制。后面仍然使用的是同一套 vLLM 部署。

例如，假如模型和硬件支持支持 32K 上下文，可以这样设计

```
请求 → 模型网关识别业务 
				├─ 普通业务：8K 上限、常规并发和排队规则 
				└─ 豁免业务：32K 上限、更低并发、独立配额 
									↓ 
				同一个 vLLM 实例 部署上下文上限为 32K
```

这里 vLLM 是部署级上限，业务网关可以对普通业务施加更低的限制。标准 vLLM 不会收到一个「特殊业务」标签，然后切换整套业务规则。网关负责上下文权限，配额以及发往后端的在途并发控制；vLLM 按统一引擎配置调度。按业务划分出来的多个请求池，比如「关键业务的专用请求池」属于业务网关侧的逻辑队列和配额，进入同一 vLLM 实例后，不同的业务请求共享 GPU 和 KV Cache, 长请求仍然可能影响短请求的延迟。它们都受统一的后端 vLLM 实例部署的限制。

# 4. 请求池独立 token 配额

业务网关层会为分流的每个请求池分配一个「独立的 token 配额」。「独立」指的是每个业务或者请求池分别计账，分别设置上限。比如长请求池有自己的 token 额度，用完后排队。

> [!warning] 独立 token 配额设计
> 独立 token 配额的设计是为了防止其中一种业务的大量请求，挤压其他普通请求容量的情况。每个请求池或每种业务设置一个 token 配额上限，用完需要等排队，等待配额释放出来。这样把每个请求池或业务的资源占用限制在自己业务上限范围内。
> 各请求池分别设置预算，分别统计占用，由业务网关决定放行，排队，释放额度。


> [!NOTE] 注意⚠️
> 请求池独立 token 配额设计是业务网关侧独有的，是业务网关针对不同请求池自定义的限制规则。它不是 vLLM 默认内置的“按业务请求分配 token 配额” , vLLM 也不会执行这套规则，vLLM 侧没有按业务请求限制的规则，它只有 `max_num_batched_tokens` 这样的参数用来限制单论调度可以计算的 token 上限。这样的设计符合分层设计思想，因为 vLLM 后端模型部署的限制，更多于底层的执行效率相关，而不是对业务种类的划分，业务种类限制就应该前提到业务网关进行限制。

请求池的 token 配置设置一般分为两种: 「按时间的 token 配额」和「在途 token 预算」。
- 按时间的 token 配额：即每分钟，每天允许处理多少 token。限制的目的是控制流量，成本和业务用量。
- 在途 token 预算： 同一时刻，已放行且尚未完成的请求，合计可以占用多少 token 预算。限制的目的是为了控制长请求带来的资源压力。
通常，业务网关对业务进行请求池分流，后端共用一个 vLLM 部署实例的情况，更多使用第二种。

> [!example] 在途 token 预算示例
> 假如长请求上下文上限是 32K tokens. 业务网关设置长请求池 128K 在途 token 预算。每个请求：
> -  输入最多为 24K token
> -  输出最多为 8K token
> -  网关为每个长请求按 32K token 预留预算
>
>那么这类请求最多放行 4 个，第 5 个先排队，等某个请求结束，释放后再放行。实际还要满足并发限制等其他业务网关的限制规则。

# 5. 并发限制与 token 配额限制

通常在业务网关侧，我们针对请求池，除了进行 token 配额限制，还会进行并发数的上限限制。
- 在途 token 预算：这类请求的总 token 大小限制，避免少量请求占用过多容量
- 在途请求上限：同时放行的请求数量。避免短请求业务的请求池，进行大量连接，造成处理和调度压力。
所以，通常，我们在业务网关侧，会同时对一个请求池进行 token 配合限制与并发请求数限制。
