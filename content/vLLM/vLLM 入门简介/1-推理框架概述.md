# 推理框架

大模型的价值, 是要应用在各个场景里面，大模型归根结底就是一个<font color="orange">「深度学习神经网络模型」</font>。和小模型本质没有区别，不过它的「参数量比较大」，在训练时，使用的「数据量规模也很大」。所以去部署的时候，「需要计算资源也很大」。把它部署上线使用有很大挑战。

部署上线的时候，我们重点要考虑效率问题，即推理速度。
>- 站在用户角度，直接关系到等待时间，影响用户体验。
>- 对于大模型系统而言，推理速度直接影响它可以承载的并发数量。
>- 对于 AI Agent，推理效率会更敏感，一个简单的 Agent 执行的功能，可能需要和大模型交互成百上千次，如果每次慢1秒，再多次交互中的累计延迟，是无法忍受的。
> <font color="#eb4349">所以推理效率至关重要。</font>

<u>我们在一些低端的消费级显卡，资源受限的情况下，怎么把一个体量比较大的模型部署上线。这就要通过大模型的推理框架来进行适配。</u>

<font color="orange">【推理框架作用】： 大模型的推理框架，就是要能够做到把大模型成功部署上线，并且提供相应的<u>加速和优化计算方案</u>。</font>

>- <font color="lightblue">易用性</font>：要能适配主流大模型。不能有一个新的模型，还要用户自己去适配，这就不行。应该是通过现有的接入流程，在部署的时候修改一些重要参数(例如替换模型名称)。
>- <font color="lightblue">多用户支持</font>：要支持多用户。要能够做鉴权，账户验证等，包括多用户下一些安全的方案等等。业内最主流的就是 OpenAI 的那套流程，通过 API Key 去注册，做鉴权。让获得 API Key 的用户可以放心使用当前服务。还有并发，资源共享的问题。
>- <font color="lightblue">高吞吐量和低延迟</font>：它要有处理大量并发请求的能力，还要尽量保证每个请求都能得到快速响应，吞吐量要非常高。因此，不仅要考虑软件层面优化，还要考虑硬件层面的兼容，集群并发，算力分配等。

# 现有部署方案
####  `◼︎` <font color="#b48ff4">HuggingFace Transformer 本地部署</font>

只要我们有足够的算力，就可以通过 HuggingFace Transformer 套件，在本地进行部署。它<font color="orange">不是一个服务</font>，严格来说，是一个执行脚本，执行流程。意思就是说，<font color="orange">这个脚本执行完成后，这个大模型的生命周期就结束了</font>。HuggingFace Transformer 的任务执行完成之后，模型就会被清除内存。

这种方式，不能分享给其他人使用。只能在当前这个脚本的生命周期里可以调用，所以它的使用场景比较受限。并且需要足够的 GPU 算力。

优点是，它是<font color="orange">最严格</font>的私有化部署，算力在自己机器上，所有东西都在自己的机器上面，没有任何泄漏的风险。<font color="deeppink">如果多数场景下的处理单一，主要是离线线下数据处理，不是做一个线上实时服务，那就可以用这种方法去做。</font>
#### `◼︎` <font color="#b48ff4">大模型厂商提供的官方服务平台</font>

这是平时使用的 deepseek, chatgpt 等在线网页服务。这种方式就是我们平时用 APP 或者 Web 端访问大模型的方式。这种方式的最大缺点，就是没有办法批量调用。它没有办法，帮你处理一批数据，比如 1000 条，2000 条等(不可能逐条贴到对话窗口中)。

这些大模型厂商提供的服务平台，都是部署在公网上面的，服务器在外网，不在自己的私有化环境里面。调用的时候，<font color="#eb4349">你的问题和数据就会被传到大模型厂商部署服务的机器上面，记录在别人的日志文件里，这就天然造成数据外泄的风险。</font>

这种方式最大的优点就是免费。
#### `◼︎` <font color="#b48ff4">大模型 API 服务</font>

主要解决我们的批量化调用需求。我们可以自己写程序，通过调用 API 的方法，去不停的获得大模型在线推理能力。这种方法就是通过自己写程序，调用 API 接口，直接调用模型端的 API 服务。

这种方法的优点就是，我们不需要自备大的算力，只需要具备一台能够运行脚本的主机，就可以做到大量调用背后大模型的 API 服务。

但是大多数厂商，对于 API 的使用方式都是要收费的。因为大量的批量使用方式，厂商本身的算力成本也扛不住，很多卡，很多厂商都是通过租用的方式搭起来的。

<font color="orange">它的缺点就是，数据依然是会外泄的。</font>

接入的时候，参考大模型厂商的接入文档，现在基本上主流都是参考 OpenAI 的那一套接入 API 的规范。OpenAI 开发了一个 API 调用的 Client. 遵循这个 Client，只需要指定调用服务的 URL，和模型名称是什么，把对话的 message 输入给到 Client, 这样就能快速访问到背后的大模型服务，并且拿到相应答案。这个过程非常顺畅。所以之后，很多模型自己在搭建服务的时候，都遵循 OpenAI 的这套 API 访问规范。

#### <font color="#b48ff4">通过开源推理框架部署 API 服务</font>

这种对于用户使用来说，和 API 没有任何差别。差别在于，部署这个事情，是需要我们自己去做的。需要自己去做的话，就要提供环境，包括 GPU 算力。

我们需要部署的模型参数规模越大，我们需要的显存的量，以及算力的规模就会越大。

然后，就是要选择一个推理框架。推理框架现在基本都是开源的，按照文档一步步准备好模型数据，按它部署指令，把服务启动起来。也就是说整个服务都是由自己去运维和保障。在这些开源框架下，部署和运维的事情，就会变得很简单。

我们避免了数据外泄的风险，可以使用 API 服务，且 API 服务对我们来说是免费的。
