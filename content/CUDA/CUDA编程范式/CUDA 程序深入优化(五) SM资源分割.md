「SM资源分割，是一个多约束问题,哪个要素先达到上限，它就会成为约束条件。剩下的只能浪费」

一个 SM 中的资源有 block 槽，线程槽，寄存器， shared memory。

以G80为例，一个SM上，最多可以有 8 个 block slots。一个SM上的线程数最多有 768个。最多有 8K 个寄存器，每个寄存器 4 Byte. 共有 32KB memory。shared memory 有16KB。
如果 8 个block, 每个 block 96个线程，就可以获得 8 * 96 = 768，就可以占用完所有线程。如果 4 个 block, 每个block就有192个线程，但是这样，就无法支持 8 个block，最多只支持4个block. 如果每个 block 含有 256个线程，3个block支持768个线程，每个线程用10个寄存器，那没问题，但是如果用11个寄存器，就超过了8K，所以11个寄存器只能支持2个block, 只能支持 512 线程。

每个线程使用的寄存器数变多了，就会减少支持的线程数，所以会减少线程级别的并行度。这就会导致 **Performance Cliff: 增加资源用量后，导致并行性急剧下降， 以及资源占用率的急剧下降**。CUDA有一个工具叫 **CUDA Occupancy Calculator**，可以获取资源使用和占用率的情况。 

### kernel 启动参数配置

我们配置 kernel 启动参数，希望尽可能提高系统的并行度和资源占用率，有几个指导性意见：

软件的 block 数一般要大于 SM 数，这样每个SM至少有一个work-group(现在称为sub-partition)在执行计算。如果 block 数大于两倍的SM数的话，一个SM上就有多个block可以并发调度，如果一个block 在等待同步，就可以启动另一个 block。如果 block 数是 SM 数的100倍以上，对于未来设备就拥有很好的伸缩性。

block大小必须是32的倍数，warp大小是固定 32 线程，block 要切割成整数个 Warp。需要尽量多的Warp 尽可能的隐藏延时。实操中，Block 大小最少是64个线程(2个warp)，通常是 128 或 256 个线程(4 或 8 个 warp)。

延时隐藏, Latency hiding。指令按顺序发布。一个线程的任意操作数没有准备好时将阻塞等待，等待的过程就让另外的线程切换到系统中执行，以此隐藏等待延迟。实操中建议，需要足够多的线程才能完全隐藏延时。 

占用率 Occupancy，一个 SM 里激活 warp 与最大可容纳warp之间的比率。

**例如某GPU**：

- shared memory 按 block 分割，
- regesters 按线程分割：≤ 63
- thread block slots: ≤ 8
- thread slots: ≤ 1536

这些资源限定因素组成了多因素约束，这些约束导致了，同一时间在同一 SM 上启动线程的数量不同，它们每一个都可能成为影响因子。

**延时隐藏和利用率的计算**

假设 global memory 一次访存需要 400 个 cycles, 假设一条算术指令需要 2 个 cycles。我们需要 400 / 2 = 200 条算术指令来隐藏延时。假如代码中，针对每个 global memory 访存含 8 条独立指令，意思就是这8条指令不依赖于访存。它就可以插入global memory访存的延迟中去，200 / 8 ～ 26个warp。对于上面1536个线程，是48个warp, 此时占用率为 54%。注意⚠️54%的占用率，在这个例子中，超过 54% 或更高的占用率并不会带来性能的提升。

如果一条指令使用的数据，是寄存器里上一条语句写入的结果，延时大约～24 cycles. 那么就需要 24 / 2 = 13(+1) warps 来隐藏由于依赖寄存器引起的延迟，相应的利用率是 27%。
