# 1. 常用函数声明

```cpp
														 // Execute on  Callable from 
__global__ void KernelFunc() //  device        host
__device__ float DeviceFunc()//  device        device
__host__ float HostFunc()    //  host          host
```

__global__ 修饰的函数是 GPU 的入口函数，它在主机端调用，在设备端执行。

__device__修饰的函数是在设备端调用，在设备端执行。

__host__修饰的函数在主机端调用主机端执行。

**__host__ 和 __global__ 可以同时修饰一个函数，这个函数可以在设备端和主机端同时被调用和执行**。

**__global__ 函数的返回值必须是void。**

<aside>
💡

**global 和 device 函数，要特别注意**：

① 尽量少用递归(不鼓励)。大量的线程同时执行，如果代码包含递归，每个线程因为递归深度就会占用大量的资源。
② 不要用静态变量。大量线程会对这个静态变量产生同步和冲突，极大影响执行效率。
③ 少用malloc(允许但不鼓励)。设备端代码都是各个线程同时执行的。大量代码都在使用malloc, 就算每个线程分配很少的内存空间，大量的线程也会瞬间占满GPU显存。还有，malloc动态内存分配，本身的执行效率就很低。
④ 小心通过指针实现的函数调用。一定要注意指针是GPU端的，还是CPU端的。

</aside>

struct int2{

向量数据类型同时适用于 host 和 device 代码。通过函数 `make_type name` 构造。例如 int2 i2 = make_int2(1, 2), float4 f4 = make_float4(1.0f, 2.0f, 3.0f, 4.0f);

通过 .x, .y, .z and .w 的方式访问数据

```cpp
int2 i2 = make_int(1, 2);
int x = i2.x;
int y = i2.y;
```

# 4. 回顾CUDA线程层次

kernel 启动时，会在设备端启动一个完整的线程 Grid，Grid 里面包含若干线程块block。Grid 中的block数，以及每个 block 中的线程数，都是由开发者指定的「执行配置」。通过global 函数名后面紧跟<<<n, m>>>来指定。一个基本的执行情况为：

```cpp
int threadID = blockIdx.x * blockDim.x + threadIdx.x //①
float x = input[threadID];// ②
float y = func(x); //③
output[threadID] = y; //④
```

每个线程有一个编号，是这个线程在整个系统里所处的位置。上面的代码是设备端代码，它是由很多线程同时在执行。通过 grid 和 block 坐标可以计算 threadID ，它就是全局上线程的位置， 代码行①。然后我们可以通过 threadID, 将这个线程输入的数据读取到一个线程局部变量 x 中去 ，代码行②。然后再对它进行一个函数处理 func(x)，代码行③。最后再将处理结果写回到线程的输出上去，代码行④。**这是数据分块处理的典型情况**。

# 5. 线程同步

一个线程块 block 内的线程可以同步(相当于公司的一个部门内的人做事要步调一致，比如一起集合等)，**要进行同步的时候，我们需要调用 `__syncthreads()`函数，创建一个barrier 栅栏**. **每个线程在调用点，都要等待块内所有线程执行到这个地方，然后所有线程继续执行后续指令**。

```cpp
Mds[i] = Md[j];
__syncthreads();
func(Mds[i], Mds[i+1])
```

这段代码，我们把Mds[j] 放到 Mds[i] 里面去。很多线程都在做这个事，然后我们执行一个函数同时用到了i 和 i+1 的元素，如果没有放完的时候，就可能有一些问题。

<aside>
💡

`__syncthreads()` 函数创建 `barrier` 栅栏

当线程调用 __syncthreads() 时，就创建了一个栅栏 barrier。栅栏是为了同步一个 block 内的线程。只有当 block 内的所有线程都执行到这个同步点的时候，大家才一起往下执行，先执行到这里的线程要等待 block 内的其他线程。

**注意⚠️，同步都是指的线程块 block 内部的同步，没有全局同步，这是设计上的考虑，全局同步的系统开销会非常大，在很多时候是得不偿失的**。block 内的线程是在一个 SM 里执行，实现同步的系统开销就会相对较小。

**线程执行时间要尽量接近，并行系统的线程间负载均衡很重要，这决定效率。如果线程间执行时间差别过大，就会在同步点出现大量线程等待特几个别慢线程。通俗的说，就是队伍中不要出现拖后腿的。**

</aside>

![image.png](7%20CUDA%20%E7%BC%96%E7%A8%8B(%E4%BA%8C)/image%202.png)

只在块内同步，在块间或者说全局不进行同步，这个机制对于系统的可扩展性和适应性是有好处的。block 的硬件执行单位就是 SM，在 SM 内部实现同步，系统开销就较小，同时在扩展 SM 的时候，可以直接扩展，不用修改程序或其他的扩展成本。

同步本质上是破坏了并行线程的独立性。还有一个更严重的问题，就是线程同步，有可能会造成线程的死锁。比如下面的代码

```cpp
if(someFunc()){
	__syncthreads();
}else{
	__syncthreads();
}
```

这段代码执行过程中，有的线程会阻塞在上面的barrier上，有的阻塞在下面的barrier上。只要someFun() 的判断有真有假，线程间就没办法达成同步，谁也等不到谁，造成死锁。

# 6. 线程调度

软件层面启动的线程数目，通常是远远大于硬件可用的执行单元数目。

![image.png](7%20CUDA%20%E7%BC%96%E7%A8%8B(%E4%BA%8C)/image%203.png)

这里是一个 SM 处理核心，处理核心中有若干处理单元，称为 **sp(stream processor) 或 ALU**。每一个线程是放在这样的处理单元上执行的。绿色的方块就是一个sp，每个 sp 可以承载一个实际的线程执行。sp 实际上就是CUDA Core。**线程是一个软件概念，当实际物理硬件去执行的过程，我们称之为一个CUDA线程**。
sp 是之前更老一些的说法，CUDA Core 是更新一些的营销术语。它们都是 GPU 中 ALU 的一种。sp, CUDA Core，ALU 本质上说的是一回事，不过ALU包含的范围更广 (包括后面的Tensor Core)。

线程的调度有一些约束条件。

## **◼︎G8 为例**

![image.png](7%20CUDA%20%E7%BC%96%E7%A8%8B(%E4%BA%8C)/image%204.png)

它有16个SM，每个 SM 包含 8 个 sp, 共128个sp，代表它共有 128个 计算单元。

再次强调，线程是任务，是软件给它发布的一些指令流，这128个实实在在的苦力(计算单元)是要实际执行这些线程计算的。

每个SM可以驻扎768个线程(可以进行上下文切换) ，驻扎的意思就是允许那么多个线程放在一个SM里，**不一定实际正在被执行，有可能正在等待上下文切换**。或者说，每一个SM的上下文空间，能够存储768个线程，或者被分为768个上下文小份。

16个SM，就可以同时执行 16 * 768 = 12288个线程。也就是说，这样一个芯片，可以有12288个线程同时在上面进行调度。调度并不意味着它要实际去执行。它有128个sp, 就意味着同一个时钟周期内，它可以并行执行 128个指令流。但是有12288个线程可以在上面不停的切换。不停切换的目的就是为了延迟隐藏。

一个 SM 上 8 个 sp, 一个 warp 32 个线程，一个 warp 需要 4 个时钟周期，完成完整的一次 warp 调度。一个 SM 上可以有 768 个线程，因此可以驻留 24 个 warp。block 的大小需要我们在软件上设置，但是 block 会调度到一个 SM 上执行。一个 block 的大小，最好不超过 24 个 warp, 也就是768个线程，不然就装不下了。如果刚好 24 个 warp, 一个 block 就刚好塞满一个 SM。

## **◼︎GT200为例**

![image.png](7%20CUDA%20%E7%BC%96%E7%A8%8B(%E4%BA%8C)/image%205.png)

GT200 有 30个SM，每个SM含有8个sp，总共240个sp。每个 SM 中可驻扎多达 8 个 block, 或1024个线程(每个block 32 个线程)。同时执行，最大240个block, 或 30720个线程可以在芯片上进行调度。

# 7. Warp 线束/线轴

Warp 是一个 block 内部的一组线程。这一组线程 ThreadIdx 的值是连续的。一个 warp 以32个线程为一组。比如一个 block 有 64 个线程，那么第 1 个 warp 就是 0～31号，第 2 个 warp 就是 32 ～ 63号。warp 内部的线程编号是连续的。**「Warp是作为线程调度的基本单位」**。

block 运行在一个 SM 上。一个 SM 的 sp 数目是有一个确定值，由于 block中 的线程数是很多的，我们不能用一个 block 作为一个基本的调度单位，那样太大了。用一个更小的单位Warp，它和SM有一定的设计的比值/比例的。（类比，一个部门的几十上百个人都要去餐厅吃饭。虽然是一个部门的人，但是餐厅的桌子很少，只能是有先有后，桌子就相当于硬件的调度，要一组一组的人去吃饭，一组就是一个warp）

**一个Warp里面的线程，一定是天然同步的。它从硬件上保证，warp里面的每个线程执行过程中，所有32个线程都是一起执行到相同的指令位置, 因为指令发射器，是同时发射同一条指令给 一个 warp 内的 32 个线程。**

![image.png](7%20CUDA%20%E7%BC%96%E7%A8%8B(%E4%BA%8C)/image%206.png)

比如现在有一个SM，调度3块block时。每个block都被切分成了若干warp，通过warp来去进行上下文切换，在整个 SM 上进行调度。3 个 block 是同时在SM上驻扎的，block 中的每个 warp 对应一个独立上下文。SM 在所有的 warp 上下文间切换。

线程调度的主要目的，利用线程间相互独立执行代码，充分占据处理器停滞的空隙，这样可以达到延迟隐藏的效果。

## **◼︎「SM 调度 warp 的开销是0开销」**。

block进入SM以后，每个线程会分配存放上下文的寄存器组，通常一个线程使用 32个寄存器。线程占用的寄存器，在程序执行期间独占使用，即使在等待，没有调度执行，这个线程依然占用这些寄存器，直到程序执行完再释放。

寄存器是线程单独占用的，但是调度的基本单位是 Warp。Warp 的上下文就是 Warp 内 32 个线程的上下文 + Warp 相关的控制调度状态。Warp 的控制调度状态是单独存放在 SM 硬件结构中的，可能是专用的状态寄存器或其他专用片上存储结构，不是线程使用的通用寄存器，它们不是一个概念。

由于所有驻留线程或者Warp，都是执行期间独占寄存器，也就是独占硬件资源，所以切换 warp 时候，它就像使用开关一样，直接从一个 warp，switch 到另一个 warp 上去执行，没有任何开销。

**一个 SM 上，某一特定时刻，就只会有一个warp执行。一个warp中所有线程都同步执行相同指令**。

## **◼︎Divergent Warp**

Warp 内的线程，可能沿不同分支执行，会有什么后果？这种情况，称之为 **「divergent warp」**。一个 Warp 里本来是大家一致同步的，但是有一些线程进入这个分支，有一些进入另一个分支，同一时刻大家步调就不一致了。Warp 天生要求内部线程同步，只能相互等待，先执行 if 分支，然后执行else分支的线程只能等待。然后再执行 else 分支，此时执行完 if 分支的线程也只能等待。

![image.png](7%20CUDA%20%E7%BC%96%E7%A8%8B(%E4%BA%8C)/image%207.png)

这是因为调度器没法为每个ALU设计一个独立的逻辑控制机构，如果这样，整个芯片的成本又会指数级增加。所以，**一个warp中的线程，共享一套逻辑控制机构，或者说，一组ALU，只有一套逻辑控制机构**。上面的图示有可能出现一种极端情况，只有1/8的性能，其他7个线程都在等待那一个线程的分支结束。现在的GPU已经针对这些问题做了优化，我们平时不用太特别在意这些问题。

如果一个SM上分配了3个block，每个block 256个线程，总共 768 个线程，24 个 Warp。
GT200 的一个 SM 最多可以驻扎1024 个线程，那么就相当于 32 个 warp。

# 8. 硬件调度

## **warp 线程数与SM中 sp 数目不等**

Warp 中线程数与SM 中 sp 数目并不一定相等。

**① sp 的数目小于 warp 内的线程数，比如 Warp 32个线程， SM只有 8 个sp**

这种情况分 4 批执行，即先上去8个线程，第一个周期，执行第一条指令。第二个周期在上来另外8个线程，执行第一条指….所有32个线程执行完第一条指令后，再上去第一批的8个线程，开始执行第二条指令，以此类推。本质上，我们把 32个线程执行一条指令的周期，扩大了4倍，变成了4个物理指令周期，相当于一个 Warp 中的线程在循环使用 sp。

具体说，当一个SM调度一个warp时:

> ① 指令已经预备。
② 在第一个周期 8 个线程进入 8 个 sp 并行执行。
③ 在第二，三，四个周期每个周期进入 8 个线程。
④ 因此，分发一个 warp 执行完 32个线程执行完一条指令，需要 4 个物理指令周期。
> 

**② sp 的数目大于 warp 内的线程数，比如 SM 有 128 个sp, Warp 32个线程。**

**现在新的架构下，一个SM中的sp数目已经远远大于warp的数目了，也就是一个周期可以调度多个Warp了。**

这种情况一个SM中通常会划分成多个 SMSP，SM Sub-Partition， SM子分区。每个子分区包含多个sp, 有独立的控制结构，warp scheduler 控制调度 SMSP 内的 Warp 来执行。但是，SMSP 中的 sp 数量也可能超过 32，调度的时候就会出现如下情况。

- SMSP 之间是独立调度各自的 Warp 执行的，因为 SMSP 有独立的 warp scheduler, 它可以独立调度自己子分区内的warp执行。SMSP 之间互不干扰，相互独立。
- SMSP 内部，由于 sp 数量可能超过 Warp 的 32 个线程。因此一个SMSP 内部可能驻留多个Warp。但是由于只有一个控制结构，只有一个 warp scheduler,。因此一个指令周期，只能向一个 Warp 发射。因此，可能出现 Warp Scheduler 在连续的指令周期向不同的 Warp 发射指令。

| 周期 | 单个调度器的发射动作 | 执行单元组 0 | 执行单元组 1 |
| --- | --- | --- | --- |
| 1 | 发射 Warp A 的指令 | 计算 A | 空闲 |
| 2 | 发射 Warp B 的指令 | 继续计算 A | 计算 B |
| 3 | 暂不发射 | 空闲 | 继续计算 B |

# **8. 延迟隐藏**

假设一个 kernel 包含 1 次对global memory的读操作，需要 200 cycles，并且有 4 次独立的 multiplies + adds(乘累加)操作，这个操作跟访存操作没关系，是独立的。当到了读 global memory 的操作的时候，整个系统需要停下来等待，这就是内存的延迟，我们可以通过乘累加的操作，把时隙填满。需要多少 warp 才能完全隐藏内存延迟呢？

同样假设一个 SM，同一时刻只能调度一个warp。每个warp包含 4 个 multiplies / add 操作，每个乘累加假设需要 4 个周期，执行完一个 warp 的乘累加操作需要 16 个周期。我们需要覆盖的周期数是200个。所以需要 200 / 16 = 12.5 个warp, 向上取整，就是13个warp。也就是说需要至少13个warp在 SM 上调度，才能完全掩藏访存的延迟。

# 9. 芯片架构与内存模型总结

**SM 的 sub-partiton**

SM 现在内部的 sp 越来越多，为了减少硬件复杂度，会划分为多个芯片组，每个芯片组叫做一个 sub-partition, SMSP。 每个sub- partition 都有自己独立的 warp-scheduler 以及其他一套完整的控制逻辑机构，逻辑上一个芯片组等同于一个sub-SM。 

**block, warp, sub-partition**

▪︎ **一个block只能分配到一个SM上，不能跨SM。但是在SM内部，block的 warp 是可以跨 sub-partition 的，可以垮 SMSP 子分区， 而且通常就是分散到多个子分区上执行的**。

▪︎ **block中的一个warp，分配到一个 partition 上执行。warp中的线程不能跨 partition。warp是sub-partition调度的最小单位，warp内 32 个线程整体驻留同一个 sub-partition**。

▪︎ **但是一个partition上可以有来自多个 block 的 warp。线程调度是以warp为单位的，warp-scheduler 并不识别 block 的存在，只是在 partition 内部的 warp 上下文间切换**。

▪︎ **shared memory是在block内共享，所以 shared memory 只能停留在SM级上的共享，因为block的 warp 跨多个 sub partition, 只有SM级的存储才能让它们相互通信。Shared Memory 是 SM 的内部片上存储器，和寄存器一样快，同样使用 SRAM**。

▪︎ **事实上block进入SM后，通常都是跨 sub partition 分配的，常见的分配方式就是warp ID 取模: warp 0 → sub partition 0, warp 1 → sub partition 1, …. 以此类推**。

▪︎ **block的大小是由用户指定的，在启动核函数的时候，需要指定执行配置。 而warp的大小是固定的，就是32个线程组成一个warp**。

**寄存器 Register**

线程有自己私有(分配)的寄存器，寄存器 SM 内部，可以快速读写。如果每个线程增加寄存器的用量，可能使得线程更快，但是由于硬件复杂度上来了，芯片面积是有限的，芯片内能够承载的线程数量就会减少。

寄存器是有限资源，每个 SM 的寄存器要分配给驻留在该 SM 上所有的线程。在程序执行期间，线程无论是否被调度或者正在被执行，都独占寄存器资源。只有线程结束后，才会释放。

例如，G80 每个 SM 有 8k(8192)个寄存器，可以承载 768个线程，每个线程可以分到 8192 / 768 ～ 10个寄存器。如果超出寄存器数量限制，来进行分配的话，比如每个线程分得 11 个寄存器，那可以驻留的 block 数就会减少。

由于一个block只能分配在一个SM上，如果一个block不能得到完整数目的寄存器分配，这个block就只能等待下一次分配。

如果每个线程分配 11 个寄存器，每个 block 有256个线程，本来一个SM可以分配 3 个block，但是由于每个线程 11个寄存器，768个线程需要 8848 个寄存器，SM只有8192(8K)个寄存器，这就导致SM 不够分配 3个block，因此只能分配两个block, 也就是说只有 512 个线程可以同时驻扎在SM里，16 个 warp，warp 变少意味有资源浪费，效率变低了。

**Local memory 局部存储器**

Local memory 是在「GPU 显存 DRAM」 上的 global memory 中的，它依然是线程私有的，用来存放线程在私有寄存器中溢出的数据。它的速度较慢，但是可以让线程承载大一些的数据，或者说，可以支持大一些的线程。一般用于存储线程的自动变量数组(automatic variable, 自动变量)。

**shared memory 共享存储器**

shared memory 在 SM 片内，每个 SM 都有自己的物理硬件 SRAM 的 shared memory。shared memory 按照 block 分配给 block 独享使用，block 内的线程都可以共享分配给这个 block 的 shared memory 存储区域。它跟整个L1 cache 处在同一个层次上，都是SRAM。不同的是，它是用户可操作可编程的 cache。

shared memory是整个系统中，约束block数和线程数的约束条件。也就是说，memory是线程的竞争资源。

同样G80为例，每个SM 8个 block, shared memory 16KB, 每个block 分配 2KB shared memory。如果贪心一些，每个 block 用 5KB，一个SM就只能驻扎3个 block 了。

💡

**重要**

**「寄存器容量及分配，shared memory的容量与分配，都会成为block数和线程数的约束条件」**。 

</aside>

注意⚠️：**寄存器，L1/L2/L3 cache, shared memory, 在物理上都是使用的SRAM。它们之间的大小需选择，在片内还有一个取舍平衡的问题**。

**global memory 全局存储器**

全局存储器，在GPU显存上，延迟比较长，100个周期是它的访问数量级。它是片外，可读写，随机访问。完全随机访问会影响性能。实际上它的带宽比较大，这就是 GDDR 的优势。

**constant memory 常量存储器**

它的延迟小，带宽高。它是在 GPU 显存上，但是有缓存。另外，它对GPU设备端是只读的，不会造成线程的冲突和锁存竞争的问题，所以它的速度较快。主机端可以对它进行读写，但是GPU设备端只读。它的容量不大，主要是用来存放一些线程间共用的不变的常量数据。

声明不同种类内存

![image.png](7%20CUDA%20%E7%BC%96%E7%A8%8B(%E4%BA%8C)/image%208.png)

- register作用域是一个thread, 生命周期是 kernel，kernel 退出了寄存器就被释放了。它是由编译器自动管理的，我们没法去干预它的行为。
- local memory 也是编译器去管理的，作用域是thread 和 生命周期和register一样，它们共同私有于一个线程。
- shared memory的作用域是block，block退出的时候，shared memory就会被释放， 生命周期也是kernel。

注意⚠️：shared memory 定义需要加上前缀 __shared__。它是在一个线程代码中定义，在整个block 上共享，不是一个线程有这么一个内存空间的变量。这样定义了，在 block 内部的线程中，大家看到的是同一个东西。

注意⚠️：线程，block，kernel本质上生命周期是一样的。线程结束，block结束，kernel 结束，本质上就是同时发生的。

global memory作用域是整个grid, 整个grid都是共享的。constant memory 和它是一样的。
