# 11. CUDA程序深入优化(三): 访存合并

存储优化：**「存储优化在整个 CUDA 程序设计里面，是最重要的因素」**。

由于 GPU 系统是依附于 CPU 系统的 PCIe 总线接口，我们首先要做的就是减少 CPU 和 GPU 之间的数据传输。主机端和设备端之间数据传输的带宽远小于显存 global memory 的访存带宽。比如现在最新的 PCIe Gen5, 128GB/s, 但是 SXM 显存的带宽已经到了 4.8 TB/s，差了 1～2 个数量级，数据在 CPU 和 GPU 之间传输，PCIe 总线带宽是最大的瓶颈。

<aside>
💡

**减少 CPU 和 GPU 之间的数据传输**

**① 中间数据直接在 GPU 上分配，操作和释放**。中间缓存的数据，不需要在 CPU 上做任何操作，直接在 GPU 上进行操作。

② **有时候更适合在GPU上进行重复计算**。我们有时候要算一些更新系数，对于所有线程，参数都是一致的，我们以为把它们放在 CPU 上计算，再传到 GPU 上面去，每个线程都适用，这样做就避免了重复计算，因为 GPU 代码是所有线程的共享指令流。

而实际上，GPU 有足够多的计算单元，有时候，总线传输数据的开销比重复计算的开销还要要大得多，所以，**「有时候在 GPU 上进行重复计算，反而可以获得更好的性能」**。 

③ **如果没有减少 CPU 和 GPU 间的数据传输，移植 CPU 代码到 GPU 上没有意义**。将 CPU代码移植到 GPU 上，即使做了很好的并行性，如果数据传输没有减少，可能也无法提升性能。大量时间会卡在数据传输上。

④ **组团传输**。减小系统外部的开销，大块传输通常好于小块传输。如果数据小于 80KB，性能开销就主要受延迟支配了，此时数据传输的开销跟数据的多少相关性就变低了。所以，我们要尽量避免小块的零散的数据，频繁的传输。最好是把一些数据打包到一起，一下子做大块传输。

⑤ **内存传输与计算时间重叠**。让 PCIe 传输，与 GPU 的计算时间重叠，我们可以采取双缓存模式。用两块缓存，一块做数据操作(计算)，另一块做读写。操作完之后，切换到另一块缓存上去。操作数据的缓存块，下一个时间可以用于读写，读写完的缓存块下一时间就可以用于操作。这样把内存传输与计算时间重叠起来。

</aside>

# Memory Coalescing 访存合并

**「访存合并是最重要的性能影响因子」**。Global memory 虽然带宽可以做很大，但是它的延迟比较高，大概 400-800 cycles。GDDR显存相当于一条高速公路，宽度很宽，但是延迟是指从高速公路入口到出口，即 数据一次传输所需要用的时间。

> 延迟：延迟是从发起读取操作，到获得结果可用之间的时间差，包括收发电路的处理时间。一次数据请求如果要访存，一般要经历：查询缓存(未命中) → 请求到达显存控制器 → 控制器调度请求，可能需要排队 → DRAM 选择并读出所需的数据 → 数据传回 GPU，进入寄存器。一次访存完成。这个过程中电信号的传播是光速，主要的延迟，就产生于这些步骤。
> 

在 Fermi 架构中，global memory 的读取默认会缓存到一级缓存 L1 上。通过给 nvcc 指令设置参数，`Xptxas - dlcm=cg`, 可以绕过一级缓存，只缓存于二级缓存 L2 上。

如果 warp 的读写请求落到 「L1 cache line」 上, 只需要一次传输，就可以读取整个warp 请求读取的数据，只需一次总线操作就可以了。

## 1. Cache Line

**「cache line 是缓存系统中数据传输和管理的最小单位」**。

CPU/GPU访问内存时，不是按字节或单个变量来读取，而是按固定大小的 “块” 来读取，**「这个数据块就叫做 cache line」**。即使只想读一个字节，硬件也会把包含这个字节的**整条 cache line(通常是64 或128字节)从存储区取回来，整条方放进 cache**.

这样的设计是因为**「空间局部性」**和**「DRAM的物理特性」**

**「空间局部性」**：刚访问过的地址，后连续的一段地址，马上被访问的概率很高。后续访问，很大概率直接命中 Cache, 省掉去 DRAM 的几百个周期。

**「DRAM物理特性」**：DRAM 延迟的开销大头在 “地址解析” 和 “行激活”，真正传数据反而便宜。所以一次取 1 个字节和 128 个字节，时间差不多，批量读取摊薄了固定开销。

**典型的 Cache Line 尺寸**：x86 CPU L1/L2/L3 是 64字节 Cache Line 。 NVIDIA GPU L1: 128 字节 Cache Line。NVIDIA GPU L2：32字节 sector (4个sector凑成128字节 Cache Line)。

> sector : sector就是在一个条 Cache Line 里面分成 4 个槽，每个槽 32 个字节。我们从 DRAM 上读取数据的时候，可以不按整条 Cache Line 读取，可以只读取其中的一个sector, 让缓存中其他 3 个sector保持无效。这样可以节约 3/4 数据传输量。额外预取会搬来大量无用数据，造成带宽拥挤。所以引入了 sector 概念。所以上面会有绕开 L1 使用 L2 的请求。
> 

现在理解 Cache Line 时，先不用管 sector, 就按单次读取一个 Cache Line 理解。

**注意⚠️：Cache Line 是缓存侧的地址组织方式，DRAM 本身不需要理解 Cache LIne**。

一个 Warp 32个线程，每个线程读取一个 4 字节 float, 就是128字节。
「理想状况」：32个线程要读取的数据地址连续排列，刚好落在同一条 128 字节的 cache line 里，硬件发送一次 transaction, 取回一条line，分发给32个线程，放在它们各自寄存器里。带宽利用率100% 
「最坏情况」：32个线程需要访问的 32个地址落在不同的 cache line上，硬件要取32条line, 共 32 * 128 = 4096 字节，但是我们只用了其中的128字节。带宽利用率 128 / 4096 = 3%，剩下97%的带宽全部浪费在不需要的数据上了。

**「访存模式对 GPU kernel 影响巨大，相同算法 coalesced 和 uncoalesced 之间差10倍以上」**。

cache line 是硬件透明的，代码层面我们不能指定 “读一条cache line”，是读取数据的时候，系统自动按 line 的颗粒度去搬运。这与 shared memory 不同，shared memory 是由程序员显示控制的。**「合并访存优化的是“硬件自动行为”，shared memory 的tiling操作是利用“程序员手动控制」**，两者经常配合使用，但是它们的机制完全不同。

## 2. Coalescing 合并

![image.png](11%20CUDA%E7%A8%8B%E5%BA%8F%E6%B7%B1%E5%85%A5%E4%BC%98%E5%8C%96(%E4%B8%89)%20%E8%AE%BF%E5%AD%98%E5%90%88%E5%B9%B6/image.png)

如果一个二维数组放在 global memory中。线程的访问模式，最好的就是，以行优先的模式把数组摊开一行一行之后，每个线程访问一个数据。

合并访存的硬件单位是warp，不是任意多少个线程。GPU执行一条 load 指令的时候，是以warp为单位发射的，32个线程同时执行 `LD E`, 硬件会检查这 32 个线程的目标地址。

global memory 的访问粒度是 128字节 cache line。当一个warp发射load指令的时候，硬件会把32个线程的请求地址做合并分析：

- 如果 32 个地址恰好落在同一个128字节的 cache line 里(比如32个线程各读一个 4 字节float，刚好128字节)，硬件只发出一个 memory transaction, 一次性取回128个字节，32个 float，然后分发给 32 个线程各自的寄存器，并放在Cache中。
- 如果 32 个地址分散在多个 cache line 上, 比如列优先访问行优先存储的矩阵，硬件就要发出多个 transaction, 最坏的情况就是32个线程产生32次访存，带宽利用率 1/32，

所以，**「合并访存的本质是：warp内 32 个线程的访存请求，被硬件合并成尽量少的 memory transaction」**.

<aside>
💡

**特别注意⚠️**

发出访存请求的不是一个线程，而是一个 warp, warp 的线程是严格同步执行的，所以 32 个线程是同时发出的访存请求。实际就是 warp 发出了一个访存请求，硬件分析发现这个Warp 的 32 个线程要的数据，正好在一条cache line上，就一次取回。

</aside>

对于行优先存储的矩阵，`M[row][col]`. 更合适的模式是，让warp内相邻 `threadIdx.x` 的线程访问相邻的 col， 即 M[row][threadIdx.x], 这样32个线程请求的数据，在 global memory中连续，命中同一条 cache line，达到合并访存。

如果写成 `M[threadIdx.x][col]`, 每个线程跨行访问，32个线程请求的地址为一整行 stride，每个线程踩在不同的 cache line 上，这就是典型的 uncoalesced access, 性能会差数量级。

如果 Warp内的线程编号，和它访问的数据地址，都是连续的，每个线程都是并排去访问 global memory 地址，这就称为满足合并访存条件。如果满足访存合并条件，warp(老的系统上可能支持半个warp)的线程访问 global memory 的 32， 64，或 128 位数据宽度，结果仅需 1 或 2 次 传输。

![image.png](11%20CUDA%E7%A8%8B%E5%BA%8F%E6%B7%B1%E5%85%A5%E4%BC%98%E5%8C%96(%E4%B8%89)%20%E8%AE%BF%E5%AD%98%E5%90%88%E5%B9%B6/image%201.png)

每个线程要求访问的数据宽度可能是不一样的，可能是单精度(32位)，双精度(64位)，或者是更长(128 位)。图中，蓝色的代表如果按单精度读取，每个线程访问的数据宽度为32位。一个warp访问就是 128 字节，就是图中的一个蓝色条，需要1次数据传输。如果是双精度，数据宽度 64 位，一个warp访问就是256字节，需要两次传输(一个cache line 是128字节)，这种情况下 warp 一次请求就是图上一个绿色条的数据。如果要更长128位精度，一个warp请求512字节，如图上一个红色条所示。

以单精度32位4个Byte的浮点数为例，Warp一次访存，读取128个字节，每个线程访问各自的 4 字节浮点数，即第 K 个线程必须访问同一段里面的第 K 个字，但并不是所有线程都要参与。

![image.png](11%20CUDA%E7%A8%8B%E5%BA%8F%E6%B7%B1%E5%85%A5%E4%BC%98%E5%8C%96(%E4%B8%89)%20%E8%AE%BF%E5%AD%98%E5%90%88%E5%B9%B6/image%202.png)

上面是最理想的warp访问模式。实际上，如果中间有一些交叉，那么总线传输就需要16次，一下性能就恶化了，或者出现了错位访问的问题(如上图的第二，三种情况)。但是，现在的设备，访存系统经过了很多优化和进展，第二，三种情况都能被妥善处理，能够在一个transaction内读取数据。但是，最不希望的就是出现非常凌乱的完全随机的访问，这种混乱的随机访存，对GPU的访存系统来说，压力是非常巨大的。所以，**在设计程序的时候，第一个要考虑的性能因素就是，如何设计一个规则化的合并访存的模式**。如果没有那么规则，也没有太大问题，但完全随机访存就会导致性能恶化。

我们还要避免出现一种模式，就是一个线程访问一段连续空间。就是每个线程去连续访问一段很长的地址空间，这时，访存系统没法进行合并，它只能反复读取，带宽浪费非常巨大。
