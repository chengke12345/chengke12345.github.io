# 4. GPU体系架构概述

重要名词：

**「FLOPS」**：FLoating-point Operation Per Second，每秒钟浮点运算次数。
**「GFLOPS」**: one billion FLOPS ($10^9$)，即十亿次浮点运算每秒。
**「TFLOPS」**: 1000 GFLOPS，即万亿次浮点运算每秒。

# 芯片优化路径

GPU(Graphics Processing Unit), 是一个异构多处理芯片。最初是为了图形图像数据的处理优化。

GPU 芯片与我们常用的 CPU 在一些部分上有不同的叫法。叫法不同，只是因为它针对一些特定任务做了一些优化，但是完成工作的本质上是一样的。

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image.png)

上图黄色部分的 「Sharder Core」，是一个 「渲染单元」，渲染器的核心就是最基本的 ALU 计算单元，只不过它是特定为了优化图形图像的渲染而设计的 ALU 计算单元，所以叫渲染单元，Sharder Core, 但本质上的功能，就是 ALU。
右边蓝色部分，是一些专门针对图形图像任务硬件结构。然后，GPU是一个典型的多核系统，需要一个「任务管理器 Work Distributor」

GPU 以前是专门面向图形图像的，这也是 GPU 这个设备名字的由来。而现在是通用 GPU，可以完成各种通用计算，包括常见的加减乘除等。通用 GPU 叫 GPGPU, General Purpose Graphics Processing Unit.

把其中一个 Sharder Core 渲染单元, 单独拿出来：

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%201.png)

常规的通用 GPU 中的一个执行单元，我们可以理解为一个完整的小的处理器。它有自己的一个取址译码的单元(Fetch/Decoder)，有自己的 ALU 处理核心，有自己的执行上下文存储。它的工作就是完成一条条指令流。

我们先看一下 CPU 型的核(CPU-Style Core)

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%202.png)

CPU 型的核心，在最主要的计算单元之外，还有很多优化单元，他们不是核心计算单元，他们的作用是优化或加速指令执行。CPU 内部，首先有一个很大的数据缓存。然后还有一个OoO(Out-of Order, 乱序之行)的控制逻辑，一个分支预测器，还有就是存储器的一些管理单元。

这些器件跟我们规则化的指令处理是不相关的，它只是让你处理得更快，更流畅。但是它们却占用了大量的芯片面积，以及大量的成本，CPU 价格里面这部分其实是花掉了最大部分的钱，实际上计算的部分花的成本是比较少的。

### 优化思路1: 精简结构

在 CPU 核心的架构下，我们可以进行一些优化，做一些 “精简，减肥”。第一个思路就是将针对指令进行优化的部分都去掉。形成：

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%203.png)

我们发现，真正执行指令的这部分是比较少的。我们留下真正计算的部分，精简掉那些设计目的是为了让它计算更快但是却非常消耗资源的部分。我们只留下最核心的数据通路上的这些部件。它的主要功能就是，取指，执行，以及执行上下文空间。我们把一个很复杂的 CPU，精简成它原来应该有的样子，只有它最核心的部分。

精简完了之后，原来那些资源，晶体管，芯片面积就节约出来了。我们就可以多放几个这样的计算核心，就形成了：

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%204.png)

这样我们在原来的芯片面积上，多放了一个核心。这样，我们就可以并行执行两个程序片元。

**程序片元(fragment)，就是一段程序段或程序流**。 

两个核的好处就是我们可以同时执行两个独立的程序片元，这就是我们常说的双核。它们的并行度就是2。我们把那些耗时耗力的资源全部拿掉，换成了最核心的执行单元。

既然两个可以做，我们就可以做4个, 如下：

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%205.png)

我们也可以继续增加，做到16个，如下：

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%206.png)

这样的结构，就相当于我们在整个处理器里面，设计了16个小的处理器，而且每个小的处理器都可以独立完成很复杂的工作。16个核，就可以同时处理16个指令流。(16 Cores - 16 Simutaneously instruction stream)。

这里有很重要的一个设计思路就是：这16个程序片元，我们要求它们共享相同的指令流。如果这16个程序片元如果做不同的指令流，那么它就需要复杂的控制机构。这种复杂控制机构是我们最不希望看到的开销。我们把这些不必要的开支拿掉，针对规则化的应用，大家做相同的事情，这些相同的事情，由很多不同的核去处理，我们就可以加速这样的工作。

### 优化思路2: 增加ALU单元，SIMD

既然每个程序片元都放在一个小的ALU上去执行。它们都是共享相同的程序段，也就是共享相同的指令流，这时我们是一个把数据切分成小块的工作。那么我们同样可以增加ALU的宽度(数量)。这就有了第二种优化思路。如果我们增加ALU的宽度，那么我们就可以进行SIMD的处理，单指令多数据的处理。

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%207.png)

我们一个核内部，变成了多ALU的结构。一个核，就又可以处理很多数据。这种情况下，整个处理单元就需要进行一些改进。

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%208.png)

最开始，我们是一个单独的指令流，每一个片元就是一段单独的指令流。原来的结构，可以由一个ALU组成的一个核心去完成。新的结构，我们有多个ALU的结构，那么我们就可以执行一些向量的操作。但是指令的执行逻辑不需要任何变化，只是同时处理的数据变多了。

每个核内部的ALU增加到8个，如果我们把16个核心排在一起，会有128个ALU形成一个芯片：

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%209.png)

这时就会形成16路指令流并发，128(16 Cores * 8 ALUs = 128ALUs)个程序片元同时执行。这16路指令流，理论上可以是不同的指令流，也可以是相同的指令流。这就是两种不同的设计思路。例如，对于GPU而言，它为了程序的规则化，这16路指令流是一样的，共享相同的指令流。而有些多核系统，可以承载16路不同的指令流。这两种设计思路都是允许的。

如果一个片元内，我们有多个ALUs。如果遇到分支该如何执行。

 

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2010.png)

因为ALU，如果在一个组内，它们只有一组的取址译码单元。也就是说放在一个核内，一个组的ALU只能步调一致的去做事情。如上图，当执行到true的分支时，剩下的false分支，只能等待。不能做其他工作，因为一组ALU的调度首脑，只有一个。当true执行完之后，剩下的5路才能执行false。这就会出现，并不是所有的ALU都在做有用的工作。最糟糕的情况，只有一个ALU在做有用的工作。

SIMD处理是一种设计思路，并不是总是需要设置显示的SIMD指令。因为底层的硬件可以自动把这些标量指令，变成SIMD的矢量指令，这就是所谓的矢量化。这实际就是硬件进行了指令流的共享，把相同的指令流放在一起，只是处理不同的数据，形成SIMD的处理流程。NVDIA的GPU架构就是这样设计的，即它可以在硬件层面自动完成一些矢量化的操作。

还有一个问题，停滞。当一个核心要处理的数据没有到来的时候，核心需要停滞。数据处理会很快，但是数据来的过程，会比较缓慢。还有可能有一些依赖。这时，我们需要做大量独立片元的相互切换，通过片元切换来掩藏延迟。这就是片元切换，延迟掩藏。

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2011.png)

我们给一个核分配了4个任务，ALU如果要等待，就会切换任务，在 1, 2, 3, 4之间切换。通过这种方式就延迟隐藏了，这样可以获得较高的吞吐率。每一个停滞的时间，总有其他工作填满。前提是这些工作之间没有依赖性。

延迟隐藏就是提供大量彼此独立的工作，通过这些工作去切换，去占满等待时间，这样做到延迟隐藏的效果。任何一个工作，是需要把程序执行上下文的情况存储起来，以便切换出去之后，再切换回来时，能够接着工作的进度继续执行。

因此，上下文的存储空间就很重要了。

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2012.png)

GPU 的架构里面，给每一个核心，提供了一块上下文的存储空间，称之为**上下文存储池**。上下文存储池可以分为很多小的上下文存储空间，比如18个，如下：

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2013.png)

这其实就是存了18个不同的事情。上下文的数量多，每一个上下文的大小就小。如果每个上下文更大一些，那么上下文的数量就会少。

**注意：上下文切换，可以是软件管理的，也可以是硬件管理的，或者是软硬件结合的都可以。不同的体系结构里采取了不同策略。**比如Nvidia GPU, 它的上下文切换，是由硬件来管理的，并且它的上下文非常多。

# 设计芯片

#### 我的设计

我们刚提到的整体，就可以作为一个简单的芯片设计。

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2014.png)

**16 Cores (核)**。
**8 mul-add ALUs per core, 每个核内 8 个ALU，16 cores * 8 ALUs = 128 ALUs**. 这128个计算单元，理论上可以同时计算128组数据。注意⚠️，是理论上的计算上限，实际没有那么多上下文存储。**16 simultaneous instruction stream**, 16 路指令流。
**4 context storage**，每一个核内有 4 个上下文空间。
**64 concurrent(but interleaved) instruction streams**。有16 * 4  = 64 路指令流同时加载到整个芯片。同时执行的，硬件有多少就有多少， 128个指令流。但加载上可供调度的有很多，因为可以加载多个上下文进行切换。 

上面的架构图中，就是一共有16个核，每个核中有8个ALU，有4个上下文存储空间，但每个核内只有一组程序控制单元。因此，整个芯片同时支持执行  128ALUs * 4 context = 512 片元(concurrent fragments。

如果每个ALU主频是1GHz的话，我们可以获得 256 GFLOPS(@1GHz) 的峰值计算能力。一个时钟周期执行一次 FMA，即一次乘加操作，算作两次浮点数运算，16 * 8 = 128个 ALUs 一个时钟周期就有 256 次浮点运算。一个ALU 1GHz, 它的算力就有 256 GFLOPS(@1GHz)

<aside>
💡

关于程序片元数

一个核内有 N 个 ALU，它就可以同时计算 N 组数据。一个核内只有一组指令控制逻辑，所以 N 组 ALU 共享一组指令流。但是在SIMD的模式下，这 N 组 ALU 可以处理 N 组不同的数据。注意⚠️，N 组 ALU在某一时刻，正在用同一组指令处理不同的数据的时候，它是使用同一个程序上下文，这就是真正的并行。我们可以划分核内的上下文存储空间，存放多个上下文，N个 ALU 一起在上下文间切换，形成并发。可以并发执行N * M个片元。

**重点区分N个ALU是真正的N路并行计算(N-Paralell), 使用同一个上下文。M个上下文是M路并发(M-Concurrent), N个ALU作为整体，在M个上下文间切换，进行延迟隐藏**。

</aside>

#### 理想设计

我们可以进一步把理想的设计扩展一下

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2015.png)

这个设计中有 32 核，每一个核里16ALUs,  共512ALUs,  每个核内有4个上下文存储空间，可以并发执行 512 * 4 = 2048 个片元 @1GHz， 1TFLPOS。

<aside>
💡

算力的计算

上面我们共有 512 个ALUs，每个 ALUs 是 1 GHz 的频率，总共应该是 512 GHz 频率。但一个时钟周期内执行一个FMA(Fused Multiply-Add), 即一次乘加计算。在计算算力的时候，我们把它当做2次浮点数计算。所以总共的算力峰值就是 1024GFLops = 1 TFLops。

</aside>

#### 总结：三个主要设计思路

1. 使用很多“精简”核心。去掉复杂控制逻辑，在芯片面积上加入大量计算单元，并行的处理任务。
2. 把每一个核心种塞满ALUs（在执行不同片元间共享指令流）。可以有显式的SIMD向量处理指令让ALUs并行处理向量计算，也可以硬件控制的自动向量化计算的操作。简单说，把一个计算任务可以通过设计相关指令在软件上实现向量化，也可以通过硬件在底层自动把计算任务向量化。向量化的意思就是把标量计算转换为可以并行的矢量计算。
3. 不让ALU停滞空闲。在多组片元之间，使用上下文切换，以避免停滞问题，进行延迟隐藏。

# Fermi 架构细节解析

Nvidia Geforce GTX 480 (Fermi)

Nvidia-术语描述：480 stream processors(CUDA Cores), 480个流处理器。流处理器就可以理解为一个ALU。SIMT(Single Instruction Multiple Thread), 支持单指令多线程，它和 SIMD 的基本逻辑是一致的。

通用术语描述：15 Cores, 2 groups of 16 SIMD funcitonal units, 15个核，每个核内32个 ALUs 功能单元，分为两组，每组16个ALUs。每组对应一个取址/解析控制器。

Nvidia Geforce GTX 480 内部架构为 (下图为一个完整的Core)

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2016.png)

在一个核 Core 内，有两组 ALUs,  每组有 16 个ALUs。**Core 内分两组是**因为它有两个独立的取指/解码单元。NVIDIA 把这样一个 「Core」 称为一个 **「SM(Stream Multiprocessor), 流多处理器」。**可以这样理解，ALU 是处理指令流的，所以它叫「流处理器」。一个 Core 内有多个 ALU，即多个流处理器，所以一个 Core 又叫做 「流多处理器，Stream Multiprocessor，SM」。

上面黄色边框的ALU，NVIDIA 给它取了一个名字，叫做「**CUDA核，CUDA Core」**，一个CUDA核，我们可以理解为一个复杂的ALU。

一个 SM 里有 2个组。一个组由一个fercher/decoder，再加上组内的 16 个 CUDA Core 组成。这样的一个组对应一个 **「线程束 Warp」调度执行的硬件资源**。

一个GTX 480 中，有 15个 这样的 SM，每个 SM 有 32 个 CUDA核，所以共有32 * 15 = 480 个CUDA Core。这就是480型号的来源。

Nvidia-Speak

- **SM**：Nvidia 把芯片上一个「完整的核(Core)」称为一个**「流多处理器(SM, Stream Multiprocessor)」**。
- **SMSP**: 一个流处理器中会把ALU分组，每组都有自己的 取指/译码(Fetcher/Decoder) 单元。这样的一个完整组，包含独立的取指/译码单元，加上组内的ALUs一起，称为「SMSP(SM sub partition, SM 子分区)。SMSP 是执行一个 Warp 的硬件资源。

- **CUDA Core**: 在 SM 中的一个ALU，就称为一个**CUDA Core，CUDA核**。它是执行线程 Thread 的硬件资源。

# 存储和数据访问

首先回顾一下 CPU 的访存
CPU 中缓存是非常巨大的，我们芯片面积和成本大头都在缓存上。CPU一般有多级缓存。L1，L2，L3, 一般 CPU 与内存之间的带宽大概在 25GB/s。

![image.png](4%20GPU%E4%BD%93%E7%B3%BB%E6%9E%B6%E6%9E%84%E6%A6%82%E8%BF%B0/image%2024.png)

GPU 的设计逻辑是把大量的芯片面积做成了计算单元。而计算单元要访问的存储器，放在了外面，这个部分就是显存。它的带宽也很大，达到了 150GB/s.

#### 访存带宽是非常宝贵的资源！Bandwidth is a critical resource

高端 GPU 计算能力非常强大，但是数据交换很慢。GPU 做了很多优化，但是即使数据交换得到了优化，对于GPU的处理能力来说，依然不够充分。高端 GPU 的处理能力是 CPU 的20倍往上，而它的访存带宽，大致也就在CPU的 6～8 倍。

#### 带宽测试

Task：element-wise multiply two long vectors A and B (两个长向量 A 与 B 相乘), 然后再加上C。即计算 D[ i ] = A[ i ] * B[ i ] + C[ i ];

1. Load input A[i]
2. Load input B[i]
3. Load input C[i]
4. Compute A[ i ] * B[ i ] + C[ i ] 
5. store result into D[ i ]

实际上这个计算过程很简单，主要时间花在了准备数据上。一共4条访存指令。访存等待需要花费很多时间，而计算时间很短，只需一条指令时间。实际上 GPU 使用了低于 1% 的性能，大量时间都在等待数据。就算这样，也远远高于 CPU 性能。

所有应用在使用芯片时，大多是带宽受限。带宽是非常宝贵资源。所以要尽量减少数据访存，首先就是减少不必要的数据请求。

GPU 的整个设计理念与 CPU 不同，它的缓存非常小，每一个核比起CPU来说，要小很多，GPU有一个很大的主存，主存带宽很大。大量的芯片面积都留给计算单元，大量数据存放主存当中，这就要求我们要很好的处理带宽问题。在写代码时，要尽量避免频繁访问主存。

#### 高效GPU任务应具备的条件

> 
> 
> 1. 具有成千上万的独立工作。大量利用 ALU 单元，大量片元切换隐藏延迟。
> 2. 可以共享指令流。 最适用于 SIMD 型任务处理。
> 3. 最好是计算密集型任务。这里的密集型任务和我们传统理解的有差别。尽量是计算任务，通信与计算的比例合适，不要受制于访存带宽。

这是一个高效的 GPU 任务所需要具备的条件。通常这些条件是可以转化的，有些东西表面上看起来不满足，但是通过我们优化设计和程序设计，让它满足这些条件，就可以在 GPU 上进行高效处理。
