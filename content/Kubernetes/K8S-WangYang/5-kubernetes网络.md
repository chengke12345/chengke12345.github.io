kubernetes 的网络模型假定了所有 Pod 都在一个可以<font color="orange">「直接连通的扁平的网络空间」</font>中。意思就是如果两台机器分别有一个 Pod，这两个 Pod 可以通过对方 Pod 的地址直接发送数据。
要实现这样的功能，在 Google 云平台上(GCE, Google Computing Engine)，是现成的网络模型，如果 kubernetes 被安装在 GCE 上，网络模型的事就不需要我们操心, kubernetes 假设的这个网络就已经存在了。
但是，我们现在的大多数业务都不会放在 GCE 上，可能放在阿里云，华为云，甚至是自建机房。在私有云里搭建 kubernetes 集群，就不能假定这个网络已经存在，<font color="orange">我们需要自己去完成网络假设，将不同节点上的 Docker 容器之间的相互访问先打通，然后运行 kubernetes</font>。s

我们实现网络假设的时候，有一些硬性条件
- 在不使用网络地址转换 NAT 的情况下，集群中的 Pod 能够与集群中任意其他的 Pod 进行通信，当然包含跨节点的情况。
- 在不使用网络地址转换 NAT 的情况下，在集群节点上运行的程序能够与同一节点上的任何 Pod 进行通信。
- 每个 Pod 都有自己的 IP 地址 (IP-Per-Pod)，并且任何其他的 Pod 都可以通过这个相同的 IP 地址访问它。
要在这三个硬性条件下，去实现扁平化的网络。

# 1. CNI

CNI，Container Network Interface, 是一个规范标准。只要 kubernetes 想要解决容器的网络问题，我们就可以借助 CNI 去实现相关功能。通过插件化的方式即成各种网络插件，实现集群内部网络通信。只要实现 CNI 标准中定义的核心接口操作，比如 ADD 将容器添加到网络，DEL 从网络中删除一个容器，CHECK 检查容器的网络是否符合预期等。<font color="orange">CNI 插件通常聚焦在容器到容器的网络通信</font>。

![](Pasted%20image%2020261127091430.png)

Podman, CRI-O, ContainerD, 叫做 CRI(Container Runtime)。这些运行时，借助 CNI 的库去描述一个 json 文档。这个 json 文件告诉我们这个网络插件应该怎么配置，怎么使用。然后调用插件库中的某些插件 Plugin，实现 Pod 与 Pod 间的网络通信。

CNI 是指对可执行程序的调用(exec) 程序。kubernetes 节点默认的 CNI 插件路径为 /opt/cni/bin

![](Pasted%20image%2020261127092230.png)

bin 目录下一看就是可执行程序。CNI 并不是指 HTTP，gRPC 这种网络接口或 web 接口，而是一种<font color="orange">「执行规范」</font>。只要能够满足 CNI 的接口定义，比如 add, del, check等，就可以接入当前 kubernetes 的集群里。 

CNI 通过 JSON 格式的配置文件来描述网络配置，当需要设置容器网络时，由容器运行时负责执行 CNI 插件并通过 CNI 插件的标准输入(stdin)来传递配置文件信息，通过标准输出(stdout)接受插件的执行结果。对于上面这么复杂的可执行文件，我们可以把它分为 5 类：

第一类是主程序端(Main), 第二类是 windows 的一些实现, 第三类是 IPAM，第四类是 Meta, 第五类是其他的网路容器插件。

## CNI 架构的深度理解

CNI，Container Network Interface, 是一种「容器网络插件」的标准规范。
不同厂商会遵循 CNI 规范的提供不同插件实现。这样的插件叫做 <font color="#45ce6e">「CNI 插件」</font>，它是以<font color="#45ce6e">「二进制可执行程序」</font>的形式供容器调用。
CNI 规范里的功能不可能在一个可执行文件里全部完成，有些功能是否使用或使用顺序应该是可以配置的，所以 CNI 规范里面的功能，实现时被拆分为了多个可执行文件，进行分工。多个二进制可执行文件组合在一起，形成一套完整的可执行程序，就如图中所示：

![](Pasted%20image%2020261127092230.png)

这套完整的可执行程序，就是 <font color="#45ce6e">「一套 CNI 插件」</font>。它们进行分工，主插件会调用另一个负责子任务的插件，所以会看到上面一串可执行程序。

不同的 CNI 插件，可以有不同的底层实现，可以有不同取舍。但是它们都遵循 CNI 标准规范，要实现里面规定的标准行为比如，ADD，DEL，CHECK 等。

CNI 插件的调用方是「容器运行时，CRI，Container Runtime」，被调用方是 CNI 插件。在容器被构建的时候，构建容器的程序 CRI 如 containerd 就会调用 CNI 插件，来完成容器的网络配置和接入。而 containerd 在调用的时候，并不会关心具体实现，它只需要按照 CNI 标准规范进行调用，所有遵循 CNI 标准的实现，都是统一标准的调用方式。

> [!tip] 运行时，CNI标准，CNI 插件之间的关系
> 运行时调用插件，规范本身不运行，不调用任何东西，它只是 运行时和网络实现之间的标准边界。概括就是 CNI 定规则，运行时按规则调用插件，CNI 插件具体干活。

上面的 bin 目录下，是把好些插件一起封装进来，有的负责不同接入方式，有的负责分配 IP 等子任务，可以搭配使用。这一套 bin 目录下的二进制文件，叫做「一套 CNI 实现」。但是可以有多套实现方案，它们都是在解决“整个 Pod 怎么联网”的问题，底层技术可以不同，但实现了统一套 CNI 标准接口。containerd 用的是同一种方式发起“把这个 Pod 接入网络”的请求，统一的调用方式，不是具体如何加入网络。

虽然我们调用 CNI 网络插件的方式是遵循标准的，但是不同的实现，在具体调用的顺序和调用组合上可能会不同，比如都是 ADD，DEL，CHECK，这一套二进制文件。但是不同的实现，可能就有不同的调用顺序，使用不同的具体插件，传递的具体参数，插件链，列表顺序都各有不同。如何使用这一套 CNI 网络插件的 "使用说明" 就放在一个 JSON 文件中。通常，一套 CNI 插件实现会提供一个 JSON 文件，常见扩展名是 .conflist 或 .conf，它说明了如何使用这套 CNI 插件实现。containerd 就是按照 JSON 文件中描述的 ”调用步骤说明“，去执行具体的插件调用的。所以 CNI 插件与容器的调用关系，可以用下面的架构图来描述：
